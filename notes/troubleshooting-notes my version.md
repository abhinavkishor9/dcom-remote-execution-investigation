# Troubleshooting Notes

## 1. DCOM Was Already Enabled

### Observation

The registry check returned:

```text
EnableDCOM
----------
Y
```

### Interpretation

DCOM was already enabled on the Windows endpoint.

No configuration change was necessary.

### Lesson

Do not modify normal Windows configuration merely to create an artificial suspicious condition.

The following finding is baseline information:

```text
EnableDCOM = Y
```

It is not evidence of compromise.

---

## 2. RPC and DCOM Services Were Already Running

The following services were running:

```text
RpcSs
DcomLaunch
RpcEptMapper
```

### Interpretation

These services provide normal Windows RPC/DCOM functionality.

### Lesson

A running RPC/DCOM service does not establish that DCOM was used for malicious remote execution.

Service state should be treated as baseline context.

---

## 3. Multiple Dllhost Processes Were Present

The process check identified multiple `dllhost.exe` instances.

Observed paths included:

```text
C:\WINDOWS\system32\DllHost.exe
C:\WINDOWS\SysWOW64\DllHost.exe
```

### Interpretation

Multiple COM Surrogate processes can exist during normal Windows operation.

### Lesson

Avoid the assumption:

```text
dllhost.exe
    +
DCOM
    =
Attack
```

A useful investigation requires additional evidence such as:

- Timestamp
- Command line
- Parent process
- User
- Network activity
- Associated COM activity

---

## 4. TCP/135 Was Listening

TCP/135 was observed listening on IPv4 and IPv6.

The owning process was:

```text
svchost.exe
```

### Interpretation

This is consistent with the RPC Endpoint Mapper.

### Lesson

A TCP/135 listener establishes that RPC infrastructure is available.

It does not establish that a remote DCOM operation occurred.

---

## 5. TCP/445 Was Also Listening

TCP/445 was observed in the listening state.

### Interpretation

This is consistent with SMB functionality on the endpoint.

### Lesson

TCP/445 is relevant when investigating lateral movement and Windows remote administration, but its presence does not establish DCOM activity.

---

## 6. The Controlled COM Test Was Local

The test used:

```powershell
$ComObject = New-Object -ComObject Shell.Application
$ComObject.GetType().FullName
```

The result was:

```text
System.__ComObject
```

### Limitation

This demonstrated local COM object creation.

It did not create a genuine remote DCOM scenario between two endpoints.

### Lesson

The lab should describe this accurately as:

> Controlled local COM activity

rather than:

> Confirmed DCOM remote execution

---

## 7. Sysmon Events Appeared Shortly After the Test

The controlled test timestamp was:

```text
2026-10-03 08:08:47.187 +05:30
```

Sysmon Event ID `1` events began around:

```text
08:08:49
```

### Interpretation

Process creation telemetry was observed shortly after the test.

### Limitation

The extracted Sysmon messages did not expose complete process details.

The output was essentially:

```text
Process Create:...
```

without enough information to identify the executable or execution chain.

### Lesson

Timestamp proximity is useful for correlation, but:

```text
Temporal proximity
    !=
Causation
```

Complete fields should be reviewed before assigning a process to the COM test.

---

## 8. DistributedCOM Event 10010 Occurred Before the Test

The observed DistributedCOM Event ID `10010` occurred at:

```text
03-10-2026 07:49:02
```

The controlled test occurred at:

```text
03-10-2026 08:08:47.187 +05:30
```

### Interpretation

The DCOM error preceded the controlled test.

### Lesson

The Event ID `10010` should not be presented as evidence generated by the controlled test.

It is a separate DCOM-related event unless additional evidence establishes a relationship.

---

## 9. DistributedCOM Did Not Have a Separately Named Log

The following command was tested:

```powershell
Get-WinEvent -ListLog *DistributedCOM*
```

It returned no event log matching the wildcard.

However, the DistributedCOM provider was visible through the Windows System log.

### Interpretation

A provider does not necessarily have a dedicated event log with the same name.

### Lesson

When investigating Windows events, check:

```text
Log Name
Provider Name
Event ID
Timestamp
Message
```

rather than assuming the provider name is also the event-log name.

---

## 10. Authentication Events Were From an Earlier Date

Event ID `4624` records were observed around:

```text
28-09-2026 07:21:13
```

through:

```text
28-09-2026 07:21:30
```

The controlled DCOM test occurred on:

```text
03-10-2026
```

### Interpretation

The observed 4624 events were several days earlier.

### Lesson

Do not use unrelated authentication events simply because they are the correct event ID.

Authentication evidence must be correlated using:

```text
Timestamp
Account
Logon Type
Source Address
Authentication Package
```

---

## 11. Wazuh FIM Alert Was Not Automatically DCOM-Related

Wazuh reported a registry integrity change associated with:

```text
svchost.exe
```

The event involved changes to:

```text
MD5
SHA1
SHA256
```

### Interpretation

This is valid Wazuh FIM telemetry.

However, no sufficient evidence established that the registry change was caused by DCOM activity.

### Lesson

An alert appearing during the same investigation does not automatically belong to the same attack chain.

Before correlating Wazuh events, compare:

```text
Host
Timestamp
User
Process
Artifact
Network Activity
```

---

## 12. Remote DCOM Execution Was Not Demonstrated

The lab did not establish the following complete chain:

```text
Remote Source
     |
     v
Authentication
     |
     v
RPC/DCOM Connection
     |
     v
Remote Process Creation
```

### Interpretation

The available evidence does not support a conclusion of confirmed remote DCOM execution.

### Lesson

A lab can still produce valuable DFIR evidence when the expected malicious technique is not demonstrated.

Documenting what could not be established is part of the investigation.

---

## 13. Why the Lab Is Still Valid

The lab successfully demonstrated several investigation concepts:

- Establishing DCOM configuration
- Identifying RPC/DCOM infrastructure
- Establishing process baselines
- Identifying RPC listeners
- Generating controlled COM activity
- Recording an exact test timestamp
- Reviewing Sysmon process telemetry
- Reviewing DistributedCOM events
- Reviewing authentication telemetry
- Reviewing Wazuh FIM telemetry
- Separating related-looking artifacts
- Avoiding unsupported conclusions

The main learning point is that **an investigation does not need a confirmed attack to demonstrate sound DFIR methodology**.
